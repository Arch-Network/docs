This page describes the objects a Prime margin account is made of, the arithmetic that
turns them into a health factor, and what each field means to a builder who is going to
display it or act on it.

Every object on this page is an Arch Prime object. The account, its positions and the
collateral registry are the business's: Arch Prime defines them, sets their parameters and
acts on them. The environment they are held and updated in is Arch Network's.

## The three objects

A margin account holds an owner, a set of positions, and a set of debts, and derives a
single health factor across all of them. Positions are valued through a collateral
registry, which is where the risk parameters live.

The pseudocode below is the shape of the model, not a wire format. Field names are chosen
for explanation.

```
MarginAccount {
    owner            // the identity that controls the account
    positions[]      // what the account holds
    debts[]          // what the account owes
    healthFactor     // derived across all of the above — not an input
}

Position {
    assetId          // which asset this position is in
    quantity         // how much of it the account holds
    liquidationRank  // where this position sits in the closeout order
}

CollateralRegistryEntry {          // one per eligible asset
    assetId
    valuationSource                // where price or NAV comes from
    haircut                        // the discount applied to market value
    maxAccountWeight               // cap on this asset's share of one account
    liquidationRank                // closeout order: lower is unwound first
    borrowEligible                 // may this asset support new borrowing
    redemptionSLA                  // how long redeeming it back into cash takes
}
```

### What each field means to you

**`owner`** — the account is the client's. Integrating does not make your product the
owner, and nothing in the read-only pattern requires it to be.

**`positions[]`** — every asset the account holds, including collateral posted and
positions the account deployed into. This is the important structural point for anyone
coming from a lending-protocol mental model: the deployed position stays inside the
account and counts toward collateral value. It is not an external holding the account has
a claim on.

The receipt representing a deployed position is a transferable instrument; the client
simply never has custody of it, because it is minted into the margin account. The
enforcement property is possession, not transferability. Do not build UI or copy that
describes the position as non-transferable — closeout can be executed as a sale of the
receipt, which depends on it being transferable.

**`quantity`** — held units, not value. Value is computed at read time from the
registry's valuation source, which is why two reads seconds apart can disagree.

**`liquidationRank` on a position** — the closeout order, ascending. Deployed strategy
positions are rank 1. Bitcoin is rank 99. Bitcoin is the last thing touched. If you show a
user what a liquidation would do to them, this is the field that answers it. The field says
the order a position is unwound in; it does not say by which route, so do not render rank 1
as "will be redeemed."

**`debts[]`** — outstanding borrowing. In V1 this is what the account owes against the
isolated pool it borrowed from, not a netted obligation across the account.

**`healthFactor`** — derived, never supplied. Store it if you must, but treat it as a
cached computation with an age, not as a fact.

**`valuationSource`** — the input that decides whether your displayed health factor is
trustworthy at all. For a price-quoted asset it is a price; for a deployed strategy
position it is a NAV, which updates on the strategy's cadence rather than the market's.

**`haircut`** — the discount applied before an asset counts as collateral.
`haircut = f(price volatility, enforcement certainty, unwind route)`. The unwind route is
decisive and is the input most often forgotten. It has two forms that fail differently:
redemption is slow but contractual, and secondary-market depth in the receipt is fast but
conditional and withdraws under stress.

**`maxAccountWeight`** — a cap on how much of a single account one asset may represent. In
V1 this is close to theoretical, because V1 runs one whitelisted strategy, which means
100% concentration by construction. That is acceptable only because the strategy is
hand-underwritten, and it is not a precedent — per-strategy and per-manager caps arrive in
phase two. Build the field in; do not assume its V1 value is the value it will keep.

**`borrowEligible`** — whether the asset supports new borrowing, which is not the same as
whether it counts as collateral. An asset can carry value in the account and still not
extend buying power.

**`redemptionSLA`** — how long it takes to redeem the asset back into cash. It is one input
to rank, not the test. The rank-1 test is whether the position can be unwound inside the
liquidation window by either route — the receipt sold, or the position redeemed with the
strategy. A position with a deep secondary market can hold rank 1 despite long redemption
terms; a position with neither a workable redemption window nor executable depth cannot hold
it at all. So do not derive eligibility, or a user-facing exit estimate, from this field
alone.

Note what follows for the registry structure: depth in the receipt's market is an input to
the same test and has no field above. Whether it is recorded in the registry at all is
unspecified.

## The margin arithmetic

Two lines, one condition:

```
collateralValue = Σ over positions ( quantity × price × (1 − haircut) )

healthFactor    = collateralValue / totalDebt

liquidation is triggered when healthFactor < 1
```

That is the whole of it. There is no second model running underneath, and no smoothing
term. A builder who reproduces these two lines against the same inputs will reproduce the
system's number.

The published risk parameter you can anchor to is the maximum LTV, and it carries a
qualification:

> **[OPEN — max LTV is stated as 80% in V1 per the 21 August gameplan; the figure is
> contested across the corpus and is not reconciled, so it may not be treated as a fixed
> integration constant · owner: Risk]**

> **[OPEN — liquidation threshold / LLTV is not published; do not derive one, and do not
> build colour bands or warning tiers that assume a value · owner: Risk]**

Implied LTV of a looped position, which is the number a user actually experiences as
leverage:

| Leverage | Implied LTV |
|---|---|
| 1.5× | ≈ 33% |
| 2.0× | 50% |
| 3.0× | ≈ 67% |
| 4.0× | 75% |

An 80% max LTV puts a hard ceiling at 5.0×, subject to the flag above.

## Why V1 is additive

V1 margin is deliberately additive. There is no correlation modelling. Nothing in the
health calculation asks whether two positions move together, and nothing offsets.

This matters to an integrator in a specific way: the capital efficiency gain comes almost
entirely from counting the deployed position, not from netting. And that gain has a
consequence you must carry with it — risk moves to the deployed leg, which is levered,
which is why those positions are whitelisted, underwritten, and liquidated first.

So if you are porting logic from a venue with portfolio margining, delete the netting.
True portfolio margin, heterogeneous collateral, netted risk and venue integrations arrive
in V2. In V1, what the user has is levered exposure through isolated pools, presented as a
margin-account experience.

## The constraint that binds, and why your UI should say so

In a levered account the binding constraint is not Bitcoin's price — it is the deployed
position's NAV. For an account with equity `E` and deployed position `V`, the impairment
that wipes equity is:

```
impairmentThatWipesEquity = E / V
```

Illustrative arithmetic, not a product parameter: 1 BTC at $100,000 posted as collateral,
$500,000 deployed, $500,000 of debt. A 20% strategy impairment wipes the client at full
Bitcoin value, while a 100% Bitcoin drawdown leaves the account whole. Presented as
arithmetic to show which term dominates, not as a claim about either asset.

A product that shows a Bitcoin price chart next to a Prime account, and nothing about the
deployed position's NAV, is showing the user the term that matters least.

## What you supply, what Arch Prime and Arch Network supply, what is not yet available

**You supply:** the display, the rounding and unit conventions in your own product, an
explicit age or timestamp next to any health figure you show, and your own decision about
what to do when a valuation input is stale.

**Arch Prime supplies:** the account, position and registry objects; the derived health
factor; the haircut, rank, weight, eligibility and unwind parameters that feed it.

**Arch Network supplies:** the execution environment those objects live in, and the
authorization and settlement of the Bitcoin leg when a rank 99 position is reached.

**Not yet available:** a published liquidation threshold; a reconciled max LTV; the
valuation-source and staleness metadata described above; and any netting behaviour, which
is a V2 property and not a V1 one.

## What does not hold

- **The health factor is not a risk score.** It is a ratio of two numbers you can compute
  yourself. It says nothing about whether the strategy behind a position is sound.
- **`healthFactor ≥ 1` is a narrow bound, and worth stating as exactly what it is.** It
  means the account is not eligible for closeout at the valuations currently in the
  system. It says nothing about the next NAV print, and it is not a statement about the
  account's exposure.
- **Additive margin is not conservative by accident.** It is a design choice for V1, and
  it means an account can be closed out on one leg while another leg would have offset it
  in a netted system.
- **These field names are not the interface.** Treat them as documentation of the model.
  The callable shapes live in the developer book.
